# 父子项层级收纳改造方案

版本：v1.0  
状态：待评审 / 可进入研发排期  
适用范围：`List`、`Spreadsheet`、`Kanban`、`Calendar`、`Gantt`

## 1. 背景

当前系统已经支持事项父子关系：

- 数据模型已有 `parent_id`
- 已有 `sub_issues_count`
- 已有子项接口与详情页子项展示能力

但五个主视图对父子关系的处理仍不统一，主要问题如下：

1. 子项在多个视图中仍作为顶层项与父项同时显示。
2. `List` / `Spreadsheet` 虽然已有局部递归渲染能力，但主列表数据仍是平铺结构，存在重复展示风险。
3. `Kanban` / `Calendar` / `Gantt` 尚未建立统一层级投影逻辑。
4. 父项删除或归档时，对子项缺乏统一、安全、可控的处理策略。
5. 批量删除 / 批量归档 / 搜索 / 分页 / 权限 / 脏数据等边界场景未形成完整规则。

本方案旨在建立统一、稳定、可灰度、可回滚的父子项层级展示与操作体系。

## 2. 目标

### 2.1 产品目标

当某个事项被设置为另一个事项的子项后：

- 子项默认不再与父项并列显示
- 子项默认收纳到父项之下
- 父项展开后可以看到子项
- 父项收起后子项完全隐藏
- 五个视图行为一致，但遵守各自视图语义
- 删除 / 归档父项时必须先询问用户对子项的处理方式

### 2.2 技术目标

- 不直接破坏现有 `issuesMap` / `groupedIssueIds` 原始数据语义
- 通过统一的“层级投影层”驱动五个视图
- 支持 feature flag 灰度
- 对分页、过滤、搜索、权限、脏数据有兜底机制
- 确保后端操作原子性，避免前端串请求造成部分成功

## 3. 非目标

本期不做以下能力：

- 不做“拖拽父项自动带动全部子项一起移动”的复杂树拖拽
- 不做“批量操作中对每个父项分别选择不同子项策略”
- 不做无限层级的视图深度展示
- 不强制把 `Kanban` 跨列子项、`Calendar` 跨日子项收纳到父项里
- 不重构整套 issue 查询接口返回树结构，本期采用前端投影方案

## 4. 现状代码结论

### 4.1 已有能力

- issue 模型中已有 `parent`
- 前端 `subIssuesStore` 已支持拉取子项、添加子项、移除子项
- `List` / `Spreadsheet` 已有递归渲染 children 的局部能力
- 详情页已有子项展开 helper 与局部可见性状态

### 4.2 已确认问题

1. 主 issue 列表当前仍把父项和子项都作为平铺元素加入 `groupedIssueIds`
2. `List` / `Spreadsheet` 递归 children 时，顶层又同时收到子项，存在重复展示根因
3. `Kanban` / `Calendar` / `Gantt` 当前直接消费平铺 `issueIds`
4. 删除、归档、批量删除、批量归档后端接口没有“子项策略参数”
5. 多入口操作尚未统一确认逻辑

## 5. 最终产品规则

### 5.1 基础层级显示规则

当 `child.parent_id = parent.id` 且父项在当前视图投影中有效时：

- 子项默认从顶层列表中移除
- 子项收纳到父项之下
- 父项收起时子项不可见
- 父项展开时子项可见
- 子项可以继续拥有子项，形成多级结构
- 建议视图默认展示深度不超过 3 层，再深层通过跳转详情查看

### 5.2 五个视图规则

#### List

- 完整树形收纳
- 顶层只显示 root issue
- 展开父项后显示 children
- 子项不再作为顶层重复出现

#### Spreadsheet

- 完整树形收纳
- 顶层只显示 root row
- 展开父项时插入子行
- 不影响 sticky 首列和横向滚动

#### Gantt

- 完整树形收纳
- 左侧 sidebar 使用树形列表
- 右侧 timeline 与 sidebar 行严格同步
- 子项使用独立子行与独立 bar
- 不再在顶层重复显示子项

#### Kanban

- 仅当父项与子项位于同一列、同一子列时允许收纳
- 若跨列或跨子列，则子项保留独立显示
- 父项卡片仍可展示子项数量
- 禁止跨列强制收纳，避免破坏状态语义

#### Calendar

- 仅当父项与子项在同一天时允许收纳
- 若跨日，则子项保留在自己的日期格独立显示
- 禁止跨日强制收纳，避免破坏日期语义

### 5.3 删除 / 归档父项规则

#### 5.3.1 显式确认优先

当用户主动对父项执行以下操作时，必须先询问对子项的处理方式：

- 删除单个父项
- 归档单个父项
- 批量删除多个父项
- 批量归档多个父项
- 其他会导致父项失效的显式用户操作

#### 5.3.2 用户可选策略

删除父项：

- `父项和子项一起删除`
- `仅删除父项，释放子项为顶层项`
- `取消`

归档父项：

- `父项和子项一起归档`
- `仅归档父项，释放子项为顶层项`
- `取消`

#### 5.3.3 释放规则

当用户选择“释放子项”时：

- 仅释放被操作父项的直接子项
- 这些直接子项的 `parent_id = null`
- 更深层后代保持相对树结构不变

示例：

- 原结构：`A -> B -> C`
- 删除 `A` 且选择“释放”
- 结果：
  - `B.parent_id = null`
  - `C.parent_id = B`

### 5.4 异常兜底规则

以下情况不弹确认框，因为不是当前用户显式触发：

- 历史脏数据：父项不存在
- 权限变化：父项不可见
- 分页未加载到父项
- 数据迁移异常
- 自引用 / 循环引用 / 非法父链

处理方式：

- 子项降级为顶层显示
- 标记为 `orphan`
- 可选展示轻提示：`原父项不可用`

## 6. 核心逻辑补全清单

本次方案必须补全以下逻辑，否则实现不完整。

### 6.1 分页

- 父项未加载、子项先加载时：子项先降级为 root
- 当父项后续加载进当前视图时：自动重新挂回父项
- 不允许分页导致子项“丢失”或“闪现”

### 6.2 搜索

- 搜索命中父项：父项显示，用户可手动展开看子项
- 搜索命中子项且父项可见：自动展开祖先链
- 搜索命中子项但父项不可见：子项降级为 root 显示

### 6.3 过滤

- 过滤后父项不可见但子项可见：子项降级为 root
- 过滤后父子都可见：按层级收纳
- 过滤不应导致命中的子项完全消失

### 6.4 排序

- root 节点按当前 `order_by` 排序
- 每个父项内部 children 也按当前 `order_by` 排序
- 不能出现“父项排在后面、子项排在前面仍被强挂”的错误结构

### 6.5 拖拽

- 拖拽默认不改变 `parent_id`
- 父项拖拽只移动自己
- 子项拖拽只移动自己
- 调整父子关系必须通过明确动作，不通过普通排序拖拽隐式完成

### 6.6 权限

- 父项可见不代表子项可编辑
- 子项可见不代表父项可编辑
- 批量级联操作必须统一做权限校验
- 禁止部分子项无权限时静默部分成功

### 6.7 脏数据防护

- `issue.id === issue.parent_id` 时直接断链
- 循环父链直接断链
- 父链深度超过安全阈值时停止递归
- 降级为 root 并记录异常

### 6.8 审计日志

必须记录：

- 父项被删除 / 归档
- 子项是“级联处理”还是“释放”
- 批量操作的数量和策略

### 6.9 计数与统计

- `sub_issues_count` 始终以服务端字段为准
- 顶层显示数量与总 issue 数可以不同
- group header count、column count、day count 等统计口径需统一定义
- 不能因为收纳导致业务统计错误

## 7. 技术方案

### 7.1 新增层级投影层

新增统一 selector/store，建议命名：

- `issue-hierarchy-selector.ts`
- 或 `issue_hierarchy_view.store.ts`

输入：

- `issuesMap`
- `groupedIssueIds`
- `groupBy`
- `subGroupBy`
- `orderBy`
- 当前 layout
- 当前过滤条件
- `subIssuesStore.subIssues`
- 展开状态
- 当前分页状态

输出：

- `getRootIssueIds(groupId?, subGroupId?)`
- `getChildren(parentId)`
- `getVisibleFlatIds(groupId?, subGroupId?)`
- `getHierarchyMeta(issueId)`
- `isNested(issueId)`
- `shouldDegradeToRoot(issueId)`
- `getAncestorChain(issueId)`

原则：

- 纯派生
- 只读
- 不直接改原始 `groupedIssueIds`
- 可灰度开关控制
- 五个视图统一消费

### 7.2 展开状态存储

新增独立展开状态，不复用详情页局部 `issue_visibility`。

建议结构：

- `expandedIssueIdsByLayout`
- key 维度：
  - `workspaceSlug`
  - `viewId`
  - `layout`
  - 可选 group signature

规则：

- 默认全部收起
- 搜索命中子项时自动展开祖先链
- 不同 layout 不共享展开态
- 返回该视图时可恢复上次展开状态

### 7.3 各视图接入方式

#### List

- `ListGroup` / `IssueBlocksList` 输入替换为 `rootIssueIds`
- 保留现有递归 block 能力
- 解决顶层重复显示

#### Spreadsheet

- `base-spreadsheet-root` 改为使用 `rootIssueIds`
- 保留递归 row 渲染
- 仅改变数据输入，不改列模型

#### Gantt

- 使用 `visibleFlatIds`
- sidebar 与 timeline 共享同一份可见线性序列
- 展开/收起只影响可见行，不影响 block 日期逻辑

#### Kanban

- 仅在同列同子列场景下将子项收纳
- 父卡片内部增加 compact children 区域
- 跨列子项降级为独立卡片

#### Calendar

- 仅在同日场景下收纳
- 父项卡片内显示 compact child rows
- 跨日子项保持在自己的日期格里

## 8. 后端接口协议设计

### 8.1 单个删除

`DELETE /api/workspaces/{slug}/projects/{project_id}/issues/{issue_id}/`

支持参数：

```json
{
  "sub_issue_strategy": "cascade_delete"
}
```

或

```json
{
  "sub_issue_strategy": "release"
}
```

说明：

- `cascade_delete`：父项和所有后代一起删除
- `release`：仅删除父项，释放直接子项为顶层项

### 8.2 单个归档

`POST /api/workspaces/{slug}/projects/{project_id}/issues/{issue_id}/archive/`

```json
{
  "sub_issue_strategy": "cascade_archive"
}
```

或

```json
{
  "sub_issue_strategy": "release"
}
```

### 8.3 批量删除

`DELETE /api/workspaces/{slug}/projects/{project_id}/issues/`

```json
{
  "issue_ids": ["p1", "p2", "i3"],
  "sub_issue_strategy": "cascade_delete"
}
```

规则：

- 若所选 issue 中包含父项，统一对子项应用同一种策略
- 本期不支持每个父项单独选不同策略

### 8.4 批量归档

`POST /api/workspaces/{slug}/projects/{project_id}/issues/archive/`

```json
{
  "issue_ids": ["p1", "p2", "i3"],
  "sub_issue_strategy": "release"
}
```

### 8.5 后端事务要求

所有涉及父项与子项策略的接口必须在单事务中完成：

- 权限校验
- issue 查询
- 子树扫描
- 删除 / 归档 / 释放
- activity 写入
- count 更新
- 返回统一结果

禁止前端通过多个请求拼接实现原子逻辑。

## 13. 验收标准

### 功能验收

- 父子关系建立后，子项默认收纳
- 父项展开后显示子项
- 收起后完全隐藏
- 不再重复显示
- 删除 / 归档父项前一定弹确认框
- 用户可选择级联或释放
- 释放后子项成为 root

### 视图验收

- `List` 正确
- `Spreadsheet` 正确
- `Gantt` 正确
- `Kanban` 同列收纳正确
- `Calendar` 同日收纳正确

### 数据验收

- `parent_id` 变更正确
- 级联删除 / 归档正确
- 释放仅影响直接子项
- 审计日志可追踪

### 稳定性验收

- 分页、过滤、搜索、权限、脏数据都不导致子项丢失
- feature flag 可随时关闭回退

## 14. 风险与规避

### 风险 1：跨列 / 跨日强制收纳破坏视图语义

规避：

- Kanban 仅同列收纳
- Calendar 仅同日收纳

### 风险 2：只改 UI，不改后端协议

规避：

- 后端接口必须支持 `sub_issue_strategy`
- 所有操作走事务

### 风险 3：只改单项，不改批量入口

规避：

- 所有删除 / 归档入口统一接入策略确认

### 风险 4：分页导致父子错位

规避：

- 父项缺失时子项降级 root
- 父项加载后重投影挂回

### 风险 5：搜索命中子项被隐藏

规避：
